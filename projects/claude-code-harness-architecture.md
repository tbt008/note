# Claude Code Harness 架构笔记

记录日期：2026-10-10
标签：项目/Agent/架构/大模型工程

## 背景

这份笔记整理自飞书 Wiki「harness工程」目录，共覆盖 15 篇文档。目标是通过 Claude Code 的源码结构，理解一个生产级 Coding Agent Harness 如何组合主循环、上下文、记忆、工具、权限、多 Agent、编辑、技能、提示词和 Hook。

总体判断：Claude Code 不是简单的“CLI 包一层模型 API”，而是一个受控工具循环 Agent。它的核心问题是让模型能够安全、连续、可验证地执行真实工程操作，同时控制上下文、成本、权限和故障恢复。

## 总体架构

一次完整交互可以概括为：

```text
用户输入
  -> QueryEngine 管理会话生命周期
  -> query() 核心循环
  -> 组装 system / tools / messages
  -> 模型流式输出
  -> 识别 tool_use
  -> 校验输入
  -> 权限判定
  -> 执行工具
  -> tool_result 作为 user message 回传
  -> 模型继续决策
  -> 没有工具调用时退出循环
```

最重要的设计是：模型是循环中的决策者，代码提供受控执行环境。循环只有在模型不再请求工具、达到轮次/预算限制、用户中断、不可恢复错误或连续压缩失败熔断时才结束。

全链路采用异步生成器，而不是回调或一次性 Promise：`query()` 边执行边 `yield` 事件，UI 实时消费 token、工具进度和错误；消费端不拉取时生产端暂停，天然具备背压和级联取消能力。

## 核心模块

### 1. 主循环与恢复

`QueryEngine` 负责会话级生命周期，包括消息持久化、配置、预算、状态恢复和 SDK 输出；`query()` 负责单次请求内的“模型调用 → 工具执行 → 继续/退出”状态机。两者分离，避免把会话管理和单轮循环耦合在一起。

工具调用可以在模型流式输出时提前排队执行。只读且并发安全的工具会并行运行，用模型继续生成的时间掩盖工具延迟；写入型工具默认串行，避免竞态。

错误处理不是简单抛给用户。系统定义了多个继续点，分别处理 Prompt Too Long、Max Output Tokens、压缩恢复等场景。可恢复错误会先被扣留，不暴露给 SDK 或 UI；恢复成功后用户无感知，全部恢复失败才向上抛出。

`orphanedPermission` 处理的是晚到的权限审批：权限结果回来时，原来的执行现场已经消失。下一次 `submitMessage()` 开始前，系统会补齐 assistant 的 `tool_use`、`tool_result` 和 transcript 链，再执行或拒绝该工具，避免历史断裂。

### 2. 上下文工程

上下文由三部分组成：系统提示词、系统/用户上下文、消息历史。系统提示词区分静态与动态边界；`CLAUDE.md`、当前日期、Git 状态、技能通告等动态信息通过 attachment 或 `<system-reminder>` 注入，避免破坏稳定前缀。

上下文治理按破坏程度从轻到重执行：

1. **Tool Result Budget**：处理“太大”的单条工具结果，完整结果落盘，上下文保留预览和引用。
2. **History Snip**：处理“太旧”的历史区间，优先移除远离当前任务的消息段。
3. **Microcompact**：处理“太旧”的工具结果，清空旧正文或通过 cache edits 从缓存中删除。
4. **Context Collapse**：将完成的历史区间投影为摘要占位，原始 transcript 保留。
5. **Autocompact**：最后兜底，让子 Agent 生成结构化摘要并重建上下文。

自动压缩后会恢复最近 5 个文件、已激活技能、计划状态、延迟工具通告等关键状态，防止模型忘记当前工作。连续 3 次自动压缩失败会触发熔断，避免无限重试造成成本放大。

提示词前缀缓存是隐形架构约束：前缀必须字节级一致才能命中。工具排序、系统提示词分段、动态信息注入位置、UI 回填不改 API 输入，都是为缓存稳定性服务。

### 3. 记忆系统

记忆分为四层：

| 层次 | 定位 | 主要内容 |
|-|-|-|
| 指令记忆 | 行为说明书 | Managed / User / Project / Local 的 `CLAUDE.md` 规则 |
| 长期记忆 | 不可推导的用户与项目知识 | user、feedback、project、reference 四类 |
| Agent 记忆 | 角色私有经验 | 某类 Agent 的偏好和方法 |
| 会话记忆 | 当前任务摘要 | 标题、状态、目标、文件、错误、工作流和进展 |

长期记忆采用封闭四类型分类，避免自由标签膨胀。`feedback` 同时保存纠正和正面确认，防止用户验证过的好方法被后续“优化”掉；`project` 必须把相对日期转为绝对日期；正文要求包含事实、`Why` 和 `How to apply`，让 Agent 能判断边界情况。

记忆系统明确不保存可从代码、Git 历史、当前上下文或 `CLAUDE.md` 推导的内容。`MEMORY.md` 是索引而非容器，召回时先扫描，再由模型评估相关性，并过滤过时、重复和不可信信息。

### 4. 工具系统

所有能力通过统一 `Tool` 接口暴露：输入 Schema、执行逻辑、权限检查、输入校验、安全语义、结果映射和 UI 渲染。执行层因此可以复用同一条流水线：找工具 → 校验 schema → 工具自检 → Pre Hook → 权限 → 执行 → 结果大小处理 → Post Hook → 生成 `tool_result`。

工具默认值采用 fail-closed：

- 默认不可并发，显式声明后才可并行。
- 默认非只读，显式声明后才跳过部分权限。
- 默认不进入自动分类器，显式提供输入后才可自动审批。

这种不对称设计牺牲一点便利性，换取更低的事故概率。Bash 叠加 AST 解析、静态验证、路径校验、命令语义、沙箱和权限规则等多层防线，避免单点绕过导致任意代码破坏。

工具结果不直接无限塞回上下文：超过阈值会落盘，只保留预览、引用和元信息；MCP 大结果同样进入统一处理。MCP 工具通过桥接层转成统一 `Tool`，并支持连接状态机、OAuth 和多种传输。

### 5. 权限系统

权限系统最终只有三种结论：`allow`、`ask`、`deny`。决策链把用户意图、静态规则、工具自检、硬性安全边界、智能判断和人工确认逐层串联，前面的层给出结论时后面的层不再执行。

关键规则包括：

- `deny` 优先拦截明显危险操作。
- `ask` 是主动交还控制权，不代表失败。
- 工具自检能针对同一工具的不同输入做细粒度判断。
- `bypassPermissions` 也受硬性安全边界约束。
- `auto` 模式会剥离过宽的危险 allow 规则，防止错误授权架空后续安全机制。
- 用户选择“允许并记住”后沉淀为精确规则，而不是开放整个工具类别。

Bash 是最复杂场景，因为 shell 语法过于灵活。仅靠正则容易被 wrapper、复合命令、引号和路径变化绕过，因此必须解析命令语义并叠加路径与破坏性操作检查。

### 6. 代码编辑策略

编辑策略围绕三个原则：最小破坏性、可验证性、抗幻觉。优先使用 FileEditTool 的 search-and-replace，而不是全文件覆盖。

Search-and-replace 的优势：

- 只改需要改的片段，降低误伤。
- old/new 内容天然可验证。
- 必须匹配现有代码，能抵抗幻觉。
- 比整文件重写更省 token。
- Diff 更小，更符合 Git 审查习惯。

编辑前必须读取相关文件，并用文件状态缓存检测并发变化。多文件编辑默认串行，配合级联保护、Worktree 隔离、原子写入和 LSP 集成，避免读到旧状态或写出部分成功的结果。全文件写入主要用于新建文件或完整重写。

### 7. 多 Agent 架构

三种模式按复杂度递增：

| 模式 | 适用场景 | 特点 |
|-|-|-|
| 子 Agent | 独立子任务 | 父 Agent 等待结果后继续 |
| Coordinator | 多 Worker 并行任务 | 协调器只编排和综合，不直接执行 |
| Swarm | 对等协作 | Agent 通过命名信箱通信 |

子 Agent 默认最大隔离：文件读取状态克隆、AbortController 新建、可变状态默认 no-op，只有显式 opt-in 才共享。工具过滤也叠加全局禁止、类型限制、异步白名单等防线。

Fork 子 Agent 的深层动机是复用父级 Prompt Cache；上下文继承是缓存共享的副产品。Coordinator 的核心约束是“不基于自己的发现直接写”，必须综合 Worker 结果；Plan 模式则把隐性信任转化为一次性方案审批。

### 8. 技能系统

技能本质是提示词模板 + 元数据 + 执行上下文，用目录和 `SKILL.md` 组织，可携带模板、配置和参考资源。它解决重复 AI 工作流的问题，例如提交、代码审查、配置变更和诊断。

技能支持用户显式调用和模型自动调用。启动时只加载 name、description、whenToUse 等 frontmatter，正文在真正调用时才进入上下文，实现“展示成本低、执行成本按需付”。

技能列表通过 `<system-reminder>` 动态注入。执行时模型调用真实的 `Skill` 工具，加载对应技能正文，再按技能继续推理。Inline 模式在当前上下文中展开；Fork 模式隔离执行并复用缓存，适合长流程或高污染任务。

与 MCP 的区别可以概括为：Skill 是通过统一入口加载工作流，MCP 是把一组具体工具直接暴露给模型；`<system-reminder>` 只是消息文本外壳，不代表对象类型。

### 9. 系统提示词

主系统提示词分为身份、运行环境、任务执行、风险评估、工具使用、语气格式和输出效率等静态部分；输出风格、语言偏好、MCP 指令、动态 Agent 等作为动态部分注入。

内置 Agent 提示词不是简单身份描述，而是完整职责边界：Explore 聚焦只读调查，Plan 聚焦方案设计，General-purpose 可执行完整任务，Verification 要求给出可复现验证。Coordinator 提示词进一步规定角色、工具、Worker 管理、失败处理、并发和结果综合。

### 10. Hook 与可扩展性

Hook 覆盖 Agent Loop 的关键生命周期：用户输入、模型输出、工具前后、权限请求、压缩前后、会话起止、子 Agent、文件变化、配置变化和停止事件。

执行流程为：快速存在性检查 → 信任检查 → matcher 匹配 → 去重 → 输入构建与并行执行 → 输出解析与聚合。命令 Hook 的退出码构成核心协议：0 表示静默成功，1 表示给用户提示，2 表示把结构化信息交回模型处理。

典型模式包括 CI 异步检查、上下文注入、团队审计、LLM 安全评估、权限自动审批和输入改写。Hook 是 Agent Loop 的横切关注点，让核心循环保持简洁，同时连接企业审计、安全策略、CI/CD 和本地工作流。

## 设计洞察

1. **模型负责决策，Harness 负责受控执行**：能力来自工具，安全来自统一协议、权限和验证，而不是信任模型本身永远正确。
2. **上下文是资源，也是成本结构**：压缩、缓存、记忆和懒加载共同保证模型看到足够信息，同时避免 token、延迟和成本失控。
3. **默认失败要偏安全**：并发、只读、自动审批、子 Agent 共享状态都默认关闭，风险必须显式声明。
4. **纵深防御接受单层失败**：规则、AST、语义检查、沙箱、分类器、用户确认和硬性边界互相补位。
5. **扩展点统一但语义不统一**：Tool、Skill、MCP、Hook 都进入统一执行框架，但分别解决动作、工作流、外部能力和横切干预。
6. **可恢复性是一等公民**：孤儿权限、输出截断、上下文超限和压缩失败都有专门路径，避免一次异常直接毁掉会话。

## 结论

Claude Code 的工程价值在于把“模型生成”升级为“可信执行系统”。它的架构始终在同时回答四个问题：模型下一步应该做什么、真实世界允许它做什么、上下文里应该留下什么、失败后如何继续。

对自研 Agent Harness 的直接启发是：先建立稳定主循环和统一工具协议，再补权限与安全；上下文治理要提前设计，不要等长会话后补压缩；记忆只存不可推导信息；所有扩展点都必须明确信任边界和失败模式。
