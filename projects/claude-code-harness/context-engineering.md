# 上下文工程

记录日期：2026-10-10
标签：Claude Code/上下文/Token/缓存

## 背景

模型决策质量取决于它看到什么。长会话会积累大量文件读取、工具输出和对话历史，超过上下文窗口；同时系统提示词和工具定义本身也可能占据很大空间。上下文工程必须在信息完整、token 成本和前缀缓存命中之间取得平衡。

## 要点

### 上下文三大支柱

1. **系统提示词**：身份、行为规则、工具使用说明，静态与动态分段。
2. **系统/用户上下文**：日期、Git 状态、`CLAUDE.md`、记忆、MCP 指令。
3. **消息历史**：用户输入、模型输出、工具调用和结果。

### 动态信息注入

`CLAUDE.md`、技能列表、MCP 指令和当前日期等通过 attachment 或 `<system-reminder>` 注入。这样可以保持系统提示词稳定前缀，减少缓存断裂。

### 五级压缩流水线

1. Tool Result 预算裁剪。
2. History Snip。
3. Microcompact。
4. Context Collapse。
5. Autocompact。

顺序从轻到重，优先局部减少 token，最后才全量摘要重建上下文。

### 前缀缓存策略

前缀缓存要求字节级一致。Claude Code 通过系统提示词分段、会话级锁存、工具数组稳定排序和缓存断裂检测维持命中率。

常见缓存友好处处：

- 保持系统提示词和工具顺序稳定。
- 避免动态内容插入稳定前缀中间。
- 只改 UI 展示，不修改发送给 API 的历史。
- 优先复用已有会话上下文。

## 示例

一次 API 请求的结构：

```json
{
  "system": ["稳定系统提示词", "动态上下文"],
  "tools": ["内置工具", "MCP 工具"],
  "messages": ["历史消息", "工具结果", "最新用户输入"]
}
```

如果每次请求都随机排序工具，系统提示词和工具定义的缓存前缀会反复失效，导致延迟和成本明显增加。

## 结论

上下文工程是隐形支柱：一方面要让模型看到足够信息，另一方面要控制 token、保持缓存稳定、避免关键工作状态在压缩后丢失。
